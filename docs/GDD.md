# 《神明不会下棋》开发案

> God Don't Know How To Play Chess
>
> 版本:v0.1 草案 | 日期:2026-09-11 | 状态:待评审

---

## 一、游戏概述

### 1.1 一句话定位

一款以中国象棋规则为基底、规则本身可以被"神明"随局改写的像素风战棋 RPG。

### 1.2 核心创意

- **象棋为骨**:开局即完整的中国象棋(9×10,纵线为路,楚河汉界,"蹩马腿""塞象眼""炮打隔子"等本土规则全部保留)。
- **神明耍赖为魂**:对手(神)会在对局中随时添加新棋子、修改棋盘、颁布临时规则、改变胜负条件——玩家必须在被篡改的规则下重新思考。
- **规则即内容**:所有棋子/棋盘/规则/胜负条件均为数据定义,可被脚本在运行时热替换,这既是玩法核心,也是 MOD 扩展性的来源。

### 1.3 游戏名

暂定《神明不会下棋》。备选:《神之一手,不予》《耍赖的神》《楚河汉界,神明止步》。

### 1.4 参考对标

| 维度 | 参考 |
|---|---|
| 美术 | FF1-6 像素风、八方旅人(HD-2D 光影/景深)、逸剑风云诀(水墨武侠像素) |
| 战斗 | 《陷阵之志》(Into the Breach)的信息透明化战棋、《将军对弈》类象棋变体 |
| 剧情结构 | 《传说之下》(规则被打破时的戏剧性)、国产武侠 RPG 的章节式叙事 |
| 规则扩展 | 《万智牌》堆叠式即时规则、桌游 Legacy(规则逐局演进) |

### 1.5 目标平台与引擎

- 引擎:**Godot 4.x**(开源免费、2D 像素支持一流、GDScript 快速迭代,且无分成)
- 平台:先 PC(Steam),后续可移植 Switch/移动端
- 分辨率:基准 640×360(16:9),整数倍放大,像素完美渲染(pixel-perfect)

## 二、双模式设计

### 2.1 模式总览

```
主菜单
├── 剧情模式(章节推进,规则随剧本演进)
├── 战役模式(加载地图包 + 棋子包,单局对弈)
│   ├── 快速对局(内置经典象棋及变体)
│   └── 自定义对局(选地图包/棋子包/规则包/胜负条件包)
└── 图鉴/成就/设定(后续版本)
```

### 2.2 剧情模式(Story Mode)

**主线梗概**:少年在村口看老人下棋,旁边一个小孩看不懂棋。少年好心教他,小孩连输几局后开始耍赖——先是偷偷挪子,然后凭空变出"骑士""魔法师"这类棋子,接着棋盘开始变形、隆起高山、裂开河流,最后连规则和胜负条件都随他心意改写……耍赖步步升级,直到被彻底将死,恼羞成怒,把少年扔进了自己创造的异世界。此时少年才发现:这个小孩是神,而他其实根本不会下棋——他只是不能输。

**结构划分**:村口这段"教棋 → 耍赖升级 → 坠入异世界"的完整弧线构成**序章**,承担全部核心机制的教学;进入异世界后的冒险即第一章的开始,**第一章及后续章节的剧情待定**(待剧本设计完成后补充,可确定的只有终局方向:与神的最终对局)。

**序章教学节点(每节点 = 1 场棋局,机制逐个引入)**:

| 序章节点 | 剧情节点 | 棋局玩法变化(教学递进) |
|---|---|---|
| 1. 村口相遇 | 少年教小孩棋规,小孩连输几局 | 完整经典象棋(玩家 vs 弱 AI),作为规则教学 |
| 2. 第一次耍赖 | 小孩偷偷挪子、悔棋,被拆穿后恼羞成怒 | 演出节点(无新机制),铺垫耍赖升级 |
| 3. 凭空造子 | 小孩变出"骑士"等幻想棋子 | 引入第一个幻想棋子,棋盘不变 |
| 4. 棋盘变形 | 棋盘隆起高山、裂开河流 | 引入地形与高低差;马腿被山"蹩"出意外效果 |
| 5. 神罚之路 | 出现禁行路线、单向通道 | 引入通路规则;"神罚之路"只能进不能出 |
| 6. 神谕 | 小孩颁布临时规则("本局炮不可过河") | 引入规则修改 UI:神谕公告 |
| 7. 耍赖到底 | 胜负条件被改写("困毙你的将不算赢,要吃掉全部兵") | 引入动态胜负条件 |
| 8. 坠入异世界 | 小孩被彻底将死,恼羞成怒把少年扔进异世界 | 序章终演出,衔接第一章 |

**第一章及后续(待定)**:异世界冒险的章节划分、同伴与剧情走向均待剧本设计。设计时需遵守的既定约束:每章引入的机制已在序章全部教学完毕,后续章节的主题应是**机制组合与深化**,而非新机制教学;终局方向为与神的最终对局。

**剧情模式要点**:
- 每次规则被修改时,以"神谕"形式高亮公告 + 音效 + 棋盘震动演出,把"被耍赖"变成可感知的正反馈而非挫败。
- 剧情对局即使输了也可推进(神会更加得意地耍赖),但赢了对局有额外奖励(棋子图鉴/隐藏支线)——避免卡关。
- 对话系统选项影响极小支线,不做 CRPG 级分支,控制工作量。

### 2.3 战役模式(Battle Mode)

定位:脱离剧情的"纯对局"沙盒。

- **加载地图**:内置编辑器导出的地图包(棋盘规格、地形、高低差、通路)。
- **加载棋子**:棋子包定义双方阵容、走法、技能。
- **单局对弈**:支持 vs AI(多档难度)或本地双人(热座)。
- 内置若干官方战役:经典象棋、残局挑战、"神的试炼"(预设好耍赖剧本的脚本对局)。

## 三、核心玩法:数据驱动的规则引擎

这是本项目**最重要**的设计决策,直接决定"神耍赖"能否成立。

### 3.1 设计原则

一切对局内容 = **数据包(Data Pack)**:

```
对局 = 地图包 + 红方棋子包 + 黑方棋子包 + 规则集 + 胜负条件集
```

引擎只实现"执行器":读入数据 → 合法性判定 → 执行 → 结算。**引擎本身不知道"马走日"**——马走日写在数据里,神改了数据,马的走法就变了。

### 3.2 棋子定义(数据示例)

```json
{
  "id": "horse",
  "name": "马",
  "faction": "black",
  "tier": "classic",
  "move": {
    "type": "leaper",
    "pattern": [(1,2),(2,1),(-1,2),(-2,1),(1,-2),(2,-1),(-1,-2),(-2,-1)],
    "blockers": ["horse_leg"]     // 蹩马腿:引用规则集里的阻挡判定
  },
  "attack": { "type": "displace" },   // 占据式:移动进敌子格即吃(象棋式)
  "action_economy": "chess",          // 走即吃,一步一事
  "hp": 1,                            // 象棋制:1 击即死;幻想棋子可 >1
  "abilities": []
}
```

```json
{
  "id": "knight_f",
  "name": "骑士",
  "faction": "god",
  "tier": "fantasy",
  "move": { "type": "rider", "pattern": [(1,2),(2,1),(-1,2),(-2,1),(1,-2),(2,-1),(-1,-2),(-2,-1)] },
  "attack": { "type": "melee", "range": 1, "power": 1, "counter": true },
  "action_economy": "tactics",        // 一回合:移动 + 攻击 各一次
  "hp": 2,
  "abilities": ["guard_ally_adjacent"],
  "flavor": "神随手捏出的西洋棋子,走法一样,却不会蹩腿。"
}
```

要点:
- **移动与攻击解耦**:`move` 管怎么动,`attack` 管怎么打,是两个独立维度(详见 3.4 攻击模型)。
- `classic` 棋子 hp=1、占据式攻击,保持象棋手感;`fantasy` 棋子可有多血、接触/远程攻击、技能、光环。
- 走法用**通用走法模型**描述:leaper(跳跃)/ rider(滑行)/ cannon(隔子打击)/ custom(脚本)。

### 3.3 走法模型(引擎必须支持的完备集)

| 模型 | 说明 | 覆盖棋子 |
|---|---|---|
| Leaper | 按固定向量跳跃,可配阻挡规则 | 马、象 |
| Rider | 沿向量滑行至阻挡 | 车 |
| Step | 沿向量走一格 | 兵/卒、将/帅 |
| Cannon | 滑行移动;吃子需恰一个炮架 | 炮 |
| Zone | 九宫/过河等区域限制 | 将、士、象、兵过河转向 |
| Script | 脚本自定义(逃生口) | 一切奇怪的神造棋子 |

规则集中的判定器(可插拔):`蹩马腿`、`塞象眼`、`过河判定`、`九宫限制`、`兵卒过河增益`。

### 3.4 攻击模型(移动与攻击解耦)

战棋的"吃"在本作中拆为**移动**与**攻击**两个独立系统,棋子数据分别声明。经典象棋棋子是"占据式攻击 + 走即吃"的特例;幻想棋子则拥有常规战棋的攻击形态。

**攻击类型完备集**:

| 类型 | 说明 | 典型棋子 |
|---|---|---|
| Displace 占据式 | 移动进敌子格,敌子即除(象棋吃法),**只随移动发生** | 全部 classic 棋子 |
| Melee 接触式 | 攻击邻近目标(默认 1 格,可配 pattern),双方各扣血,**不占据格子** | 骑士、剑士 |
| Ranged 单体远程 | 射程内指定单目标攻击,受视线(高低差/遮挡)判定 | 弓箭手 |
| Splash 范围远程 | 以目标格为中心按 pattern 造成范围伤害,可误伤 | 魔法师 |
| Script 脚本自定义 | 逃生口 | 神造奇怪棋子 |

**规则要点**:

- **action_economy(行动经济)**分两档:`chess`(象棋式,一步一事,走即吃)与 `tactics`(战棋式,一回合内移动 + 攻击各一次)。同局可混用两种棋子——这正是"神往棋盘里塞了奇怪东西"的戏剧来源。
- **接触式攻击**:近战互殴时攻击方先手;`counter: true` 的棋子被攻击时反伤 1。攻击不换位,近战对峙会持续多回合,形成战线——与象棋"一击即走"的节奏形成对比。
- **远程与视线**:射程判定要走视线检查(被高地/棋子遮挡则不可及);居高临下射程 +1(与地形系统联动)。魔法师的 Splash 可按 pattern 定型(十字/3×3/菱形),**可误伤**——范围内不分敌我,这是设计出的风险博弈。
- **血量与伤害**:classic 棋子 hp=1 保留象棋手感(被远程命中即亡);fantasy 棋子 hp/atk 由数据定义。远程棋子普遍 hp 偏低,符合战棋常规(射手怕近身)。
- **攻击目标规则**:占据式只能吃"落点"上的敌子;接触/远程攻击**不消耗目标格**,棋子原地行动。
- 神的 RuleOp(如 `GRANT_ABILITY`)可以直接改写攻击类型——"你的马这局会远程吐火"即是一条合法神谕。

### 3.5 地图与地形

```json
{
  "map_id": "village_gate",
  "width": 9, "height": 10,
  "cells": [
    { "x": 4, "y": 5, "terrain": "river", "elevation": 0, "pass_rule": "impassable" },
    { "x": 2, "y": 3, "terrain": "hill",  "elevation": 2,
      "pass_rule": "oneway", "oneway_dir": "N",
      "limit": null },
    { "x": 7, "y": 8, "terrain": "bridge","elevation": 0,
      "pass_rule": "limited", "limit": 3 }   // 全局共可通行 3 次
  ],
  "graph_mode": "grid"   // 或 "irregular":显式邻接图
}
```

- **高低差**:z 值影响射程/视线(如炮隔山不可打、车被山断路、弓手居高+射程)。
- **禁止通行** `impassable` / **单向通行** `oneway` / **有限次数** `limited`(全局计数,走完桥塌)。
- **不规则棋盘**:支持两种表达——矩形裁剪(缺角棋盘)与显式邻接图(六边形、S 形、环形棋盘均可)。

### 3.6 规则修改系统(神谕)

对局中脚本可执行的动作,统一走 **RuleOp(规则操作)** 通道:

```
RuleOp 类型:
├── ADD_PIECE / REMOVE_PIECE          // 凭空造子 / 抹除棋子
├── ADD_MAP_FEATURE / MODIFY_CELL     // 棋盘隆起 / 挖河 / 断路
├── RESIZE_BOARD                      // 改变棋盘规格
├── ADD_TEMP_RULE / REMOVE_TEMP_RULE  // 临时规则(带持续回合数)
├── SET_WIN_CONDITION                 // 替换胜负条件
├── GRANT_ABILITY / NERF_PIECE        // 强化/削弱某棋子
└── SCRIPTED_EVENT                    // 演出脚本(震屏、变天、BGM 切换)
```

临时规则示例: `"本局红炮不得过河`"、`"骑兵本回合移动力翻倍`"、`"三回合内双方不得吃子`"。

### 3.7 胜负条件

同样是数据,可组合、可被神替换:

- 经典:困毙/将死对方将帅、先失将者负
- 变体:歼灭全体指定棋子、占领指定格子 N 回合、护送某子到终点、限定回合内存活、回合数耗尽时按子力分判胜
- 剧情特殊:"少年必须撑过 20 回合"(守势玩法)

### 3.8 平衡性保护(防"神谕"变成纯粹的恶心)

耍赖是戏剧性,不是挫败感。原则:

1. **神谕必有预告**:颁布前 1 回合有征兆演出(乌云聚集),玩家至少有一步应对机会。
2. **耍赖有代价**:神每次耍赖,会消耗"神力",神力通过对局表现积累——玩家下得越好,神耍赖越少。这本身构成隐性难度曲线。
3. **规则透明**:任何时刻可打开"规则面板",查看当前生效的所有规则与胜负条件;神改动后 diff 高亮。
4. **可关断**:战役模式与二周目可开关"神谕"频率。

## 四、系统设计

### 4.1 AI 对手

- 棋类 AI 走**规则引擎同源**路线:AI 不写死任何规则,读同一份数据包做搜索,这样神改规则后 AI 立即适配。
- 方案:α-β 剪枝 + 子力/局面评估(评估函数也从数据读子力值);深度按难度分档;后期可加 MCTS。
- "神"的剧本 AI 单独一层:按剧本触发 RuleOp,与棋力 AI 解耦。

### 4.2 战斗流程(回合制)

```
回合开始 → (神谕阶段,如有)
→ 红方行动 → 结算 → 黑方行动 → 结算
→ 回合结束(临时规则倒计时、有限通路计数) → 胜负判定
```

**单方行动内序**(依棋子 action_economy 而定):

- `chess` 棋子:选择一个合法走法(走即吃,占据式),一步一事——象棋节奏。
- `tactics` 棋子:移动一次 + 攻击一次(顺序自由,可只做其一)——战棋节奏。
- 同一方两种棋子混编时,每个棋子按自己的行动经济结算,不强制统一。

信息透明原则(学陷阵之志):对方下回合的威胁范围可一键预览(移动范围与攻击范围分别显示)。

### 4.3 剧情演出系统

- 对话:立绘 + 打字机文本 + 选项(像素立绘,表情差分)。
- 神谕演出:全屏特效 + 公告 UI,是本作招牌演出,需重点打磨。
- 探索:章节间为轻量点击式/横版小地图走位(成本控制),不做开放世界。

### 4.4 存档与进度

- 剧情模式:章节存档 + 回合快照(棋局内 S/L)。
- 图鉴:遇过的棋子/地形/神谕收集,通关后解锁"神的棋谱"(复盘)。

### 4.5 MOD 与编辑器(驱动架构的免费红利)

因为一切皆数据包,顺势提供:

- **地图编辑器**:画格子、设地形/高低差/通路,导出地图包。
- **棋子工坊**:表单化定义走法/技能/数值,导出棋子包。
- 战役模式直接加载玩家自制包(Steam 创意工坊,后期)。

> 编辑器不必首发完整体:首发先给内部调试用的原始 JSON 导入,正式编辑器随 EA 迭代。

## 五、美术与音频

### 5.1 美术风格

- **像素风基准**:640×360,角色/棋子 32×32(战斗放大 64×64 或带 2 倍动画帧),场景 tile 16×16。
- 三层气质混合:
  - FF 系:Q 版比例、鲜明轮廓色、行走图 4 帧。
  - 八方旅人:景深模糊 + 体积光(神谕时刻光柱、丁达尔效应),UI 用复古边框 + 柔光。
  - 逸剑风云诀:水墨留白的场景底、宣纸纹理 UI、书法字体的章节标题。
- 棋子设计:经典象棋子做成像素木质圆棋子(带雕刻字),幻想棋子做成立绘化像素小人,两者同场时用描边统一。
- 色彩:村口 = 暖黄午后;神谕/异世界 = 高饱和诡异色(紫金);终章决战 = 红黑。

### 5.2 音频

- BGM:章节主题 + 对局 BGM(局势紧张时分层加重,神谕时切特殊 stinger)。
- 音效重点:落子声(木质清脆)、神谕钟声、棋盘隆起轰鸣。
- 建议音频中间件按 Godot 原生音频系统 + 分层播放列表即可,不必上 Wwise。

## 六、技术架构

### 6.1 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 引擎 | Godot 4.x | 免费、2D 像素首选、GDScript 迭代快;C# 可选用于 AI 模块 |
| 规则/剧本脚本 | 数据(JSON/自定义 DSL)+ GDScript 逃生口 | 大部分耍赖用数据可表达,复杂逻辑脚本兜底 |
| 存档 | JSON + 版本号迁移 | 数据包结构需向后兼容 |
| MOD 格式 | zip 包(内含 manifest + json + 贴图/音频) | 简单,社区易做 |

### 6.2 模块划分

```
god-dont-know-chess/
├── engine/                    # 纯逻辑,零渲染依赖,可无头运行(headless)
│   ├── board/                 # 棋盘、格子、邻接图、高低差
│   ├── pieces/                # 棋子实例、走法/攻击解析
│   ├── rules/                 # 规则集、RuleOp 管线、临时规则调度
│   ├── movegen/               # 合法走法生成(吃 blocker/zone 判定)
│   ├── combat/                # 攻击结算:接触/远程/范围、视线、反击、伤害
│   ├── wincond/               # 胜负条件求值
│   ├── ai/                    # 搜索与评估(读同一数据包)
│   └── replay/                # 局面快照与回放
├── data/                      # 内置数据包:经典象棋、幻想棋子、战役地图
├── presentation/              # Godot 场景、渲染、演出、UI
│   ├── board_view/            # 棋盘渲染、高亮、镜头
│   ├── battle_ui/             # 规则面板、神谕公告
│   ├── story/                 # 对话、章节流程、探索场景
│   └── effects/               # 像素粒子、震屏、光效
├── editor/                    # 地图/棋子编辑器(后期)
└── tools/                     # 数据校验器、无头对局模拟器
```

**关键约束**:`engine/` 不 import 任何渲染/节点类,保证可以用无头模式批量跑 AI 自对弈做平衡性回归测试——这是规则可篡改游戏的质量生命线。

### 6.3 核心数据流

```
加载数据包 → 构建对局状态(MatchState)
→ 玩家/AI 提交行动(走法/攻击) → movegen/combat 校验 → 应用 → 触发 RuleOp/事件
→ 回合结算 → wincond 求值 → 循环
每一次 RuleOp 产生 GameState 快照(供回放/悔棋/演出断点)
```

### 6.4 关键技术风险与对策

| 风险 | 对策 |
|---|---|
| 走法模型不完备,神造棋子表达不了 | Script 走法逃生口;先穷举经典变体做单元测试 |
| 攻击/行动经济混编的结算复杂度 | 行动提交统一为"意图(Intent)"结构,movegen 与 combat 各自校验各自执行 |
| 高低差与不规则棋盘叠加的 movegen 复杂度 | movegen 只依赖邻接图抽象,不假设矩形网格;视线检查同一套抽象 |
| AI 在动态规则下变蠢/变慢 | 评估函数从数据读子力;搜索深度降级保底;剧本局可限制神谕时机 |
| 神谕演出与逻辑不同步 | RuleOp 附带演出指令,由表现层订阅事件,逻辑先行 |
| 数据包结构频繁变更 | 所有数据带 schema_version,写迁移器 |

## 七、开发计划(里程碑)

以 1~2 人独立开发 + 外包美术/音频为基准的节奏(可按团队规模缩放):

### M0 原型验证(4~6 周)
- 纯逻辑引擎:经典象棋完整规则、走法生成、胜负判定,无头自对弈跑通
- 像素棋盘渲染 + 鼠标点选走子,本地双人
- **验收**:一局完整经典象棋可玩;引擎无头测试通过率 100%

### M1 核心机制(6~8 周)
- 数据驱动改造:棋子/棋盘全数据化;第一批幻想棋子(骑士、弓箭手、魔法师)入库
- 攻击系统:占据式/接触式/远程单体/远程范围 + 视线与反击结算
- 地形系统:高低差、禁行/单向/有限通路
- RuleOp 管线 + 神谕公告 UI
- 基础 AI(α-β,2~3 档难度)
- **验收**:"神的试炼"脚本对局:对局中棋盘隆起、规则变更、胜负条件替换全部按脚本发生;弓箭手隔山不可射、魔法师范围误伤结算正确

### M2 剧情模式(8~10 周)
- 对话/演出系统、章节流程、序章全部 8 个教学节点
- 存档、图鉴
- **验收**:序章可完整连贯游玩

### M3 战役模式 + 内容量(6~8 周)
- 地图/棋子包加载、官方战役 8~10 关、残局挑战
- 第一章及后续剧情(待剧本定稿后按需排期)
- **验收**:双模式可玩;剧情内容量视剧本进度调整,不阻塞战役模式交付

### M4 打磨与发行(6~8 周)
- 美术/音频终稿、平衡性回归(无头自对弈批量跑)、本地化、Steam 页面
- **验收**:EA/正式版发布

> 总计约 7~10 个月。若首发砍范围:剧情只含序章 + 战役 5 关,先行 EA。

### 首发裁剪建议(如果时间紧)

保留:完整规则引擎、神谕系统、剧情序章、战役 5 关、经典+3 个幻想棋子。
砍掉:第一章及后续剧情(随 EA 迭代补足)、正式编辑器(给 JSON 导入)、线上创意工坊、二周目分支。

## 九、验收清单(Playtest 核心问题)

1. 神谕发生时,玩家第一反应是"哇"还是"烦"?(核心体验试金石,每章试玩必测)
2. 不懂象棋的玩家能否通过序章教学学会基础规则?
3. 规则面板是否足以让玩家随时理解"当前世界规则"?
4. 关掉神谕后,它还是不是一款过得去的象棋游戏?(底线质量)
5. 神耍赖的"预告→发生→适应"节奏是否成立?

## 附:术语表

| 术语 | 定义 |
|---|---|
| RuleOp | 一次运行时规则修改操作,神谕的最小单位 |
| 数据包(Data Pack) | 描述棋子/地图/规则/胜负条件的自包含数据集合 |
| 神谕 | 剧情中神修改规则的演出事件,一个或多个 RuleOp + 演出指令 |
| 神力 | 神耍赖的预算资源,由对局进程积累,平衡性阀门 |
| 占据式攻击 | 移动进敌子格即吃,象棋吃法 |
| 接触式攻击 | 攻击邻近目标,双方各扣血,不占据格子 |
| 行动经济(action_economy) | 棋子单回合可执行的行动结构:chess(走即吃)/ tactics(移动+攻击) |
| movegen | 合法走法生成器,引擎核心 |
| 无头模式 | 引擎脱离渲染独立运行,用于自动化测试与 AI 自对弈 |
